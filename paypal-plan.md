# PayPal plan and contract sheet

This is the plan file that APIMatic's PayPal Context Plugin asks for (`typescript-integrate-paypal`,
Step 1): the operations in scope, the facts each call depends on, and the tables for writes that
must not run twice or whose outcome may be unknown. It is kept in step with the code.

**SDK note.** The plugin's skills document APIMatic's newer generated package (`paypal`,
`PaypalClient`, v2.29, installed from git). This build's brief pins the published
`@paypal/paypal-server-sdk` 2.5.0 (also generated by APIMatic), so the plugin's workflow and
its cross-cutting rules were applied to that package: contract facts below come from the
installed package's own type declarations (`node_modules/@paypal/paypal-server-sdk/dist/cjs/types`)
and, for the Disputes API the SDK does not cover, from PayPal's published OpenAPI document
(`paypal/paypal-rest-api-specifications`, `openapi/customer_disputes_v1.json`) plus read-only
smoke calls against the sandbox. Nothing here was written from memory.

Host: one deployment, one host. `https://api-m.sandbox.paypal.com` (`Environment.Sandbox` in the
SDK, `PAYPAL_BASE_URL` for REST). `lib/env.ts` refuses to run when `PAYPAL_ENVIRONMENT` is not
`sandbox`.

## Operations in scope

### Through `@paypal/paypal-server-sdk` (`lib/paypal/sdk.ts`)

| Operation | SDK call | Wire | Request fields set | Returns used |
| --- | --- | --- | --- | --- |
| Create order | `OrdersController.createOrder({ body, paypalRequestId, prefer })` | `POST /v2/checkout/orders` | `intent`, `purchaseUnits[0]` (`referenceId`, `invoiceId`, `customId`, `description`, `amount` with `breakdown`, `items`, `shipping`), `paymentSource.paypal.experienceContext` (`brandName`, `userAction`, `shippingPreference`, `returnUrl`, `cancelUrl`) | `id`, `status`, `links[rel=payer-action]` |
| Capture order | `OrdersController.captureOrder({ id, paypalRequestId, prefer })` | `POST /v2/checkout/orders/{id}/capture` | none in body | `purchaseUnits[0].payments.captures[0].id` and `status` |
| Get order | `OrdersController.getOrder({ id })` | `GET /v2/checkout/orders/{id}` | | items, shipping address, trackers, payer |
| Add tracking | `OrdersController.createOrderTracking({ id, body })` | `POST /v2/checkout/orders/{id}/track` | `captureId` (required), `trackingNumber`, `carrier: OTHER`, `carrierNameOther`, `notifyPayer` | updated order |
| Get capture | `PaymentsController.getCapturedPayment({ captureId })` | `GET /v2/payments/captures/{id}` | | `customId`, `invoiceId`, `sellerProtection`, `supplementaryData.relatedIds.orderId`, `sellerReceivableBreakdown` |
| Search transactions | `TransactionSearchController.searchTransactions({ startDate, endDate, transactionId, fields })` | `GET /v1/reporting/transactions` | date window of at most 31 days | `transactionDetails[]` (may be empty for about 3 hours after a payment) |

Errors: every SDK call rejects with `ApiError` (`statusCode`, `headers`, `result`). `sdkCall()` in
`lib/paypal/sdk.ts` converts it to this app's `PayPalError`, keeping `status`, PayPal's `name`,
the first `details[].issue` and the `PayPal-Debug-Id`.

### Plain REST with the shared OAuth helper (`lib/paypal/http.ts`, `lib/paypal/disputes.ts`, `lib/paypal/webhooks.ts`)

| Operation | Wire | Body | Notes verified in the sandbox |
| --- | --- | --- | --- |
| OAuth token | `POST /v1/oauth2/token` | `grant_type=client_credentials`, Basic auth | cached until 60 s before `expires_in` |
| List disputes | `GET /v1/customer/disputes?page_size=50` | | a new dispute takes 3 to 4 minutes to appear here; `GET` by id works at once |
| Show dispute | `GET /v1/customer/disputes/{id}` | | `links` change with state; only act on what is listed |
| Provide evidence | `POST .../provide-evidence` | multipart: part `input` = `{"evidences":[{evidence_type, notes, evidence_info}]}` as `application/json`, then file parts | one evidence type per call; only types PayPal lists with `source: REQUESTED_FROM_SELLER` |
| Send message | `POST .../send-message` | `{"message"}` | inquiry stage only |
| Make offer | `POST .../make-offer` | `{"note", "offer_type", "offer_amount"}` | inquiry stage only; `offer_type` must be in `allowed_response_options.make_offer.offer_types` |
| Accept claim | `POST .../accept-claim` | `{"note", "accept_claim_type"?}` | PayPal refunds the buyer |
| Acknowledge return | `POST .../acknowledge-return-item` | `{"note", "acknowledgement_type"}` | not-as-described cases after a return |
| Appeal | `POST .../appeal` | multipart like provide-evidence | only when `appeal` is in `links` |
| Escalate | `POST .../escalate` | `{"note"}` | inquiry stage; the case becomes a claim a few minutes later |
| Require evidence (sandbox) | `POST .../require-evidence` | `{"action": "SELLER_EVIDENCE"}` | sandbox only, needs the link |
| Settle (sandbox) | `POST .../adjudicate` | `{"adjudication_outcome": "SELLER_FAVOR"}` | sandbox only, needs the link |
| Verify webhook | `POST /v1/notifications/verify-webhook-signature` | transmission headers, `webhook_id`, raw event | expects the exact body bytes |
| Register webhook | `POST /v1/notifications/webhooks` | `url`, `event_types` | `pnpm paypal:webhook <url>` |

### Through `@paypal/agent-toolkit` (`lib/agent/tools.ts`)

`list_disputes`, `get_dispute` and `accept_dispute_claim` come from the toolkit. `accept_dispute_claim`
moves money, so it is wrapped: the wrapper re-reads the dispute, checks `accept_claim` is in `links`,
checks the merchant's thresholds, and only then lets the toolkit call PayPal.

## Durable writes

Every write below follows claim, then call, then record. The claim is a row in the desk document
(`filings[<dispute id>:<action>]`) written before PayPal is called.

### Duplicate claims

| Write | Where the claim is stored | What rejects the second one | Where that rejection is caught | Where in the code |
| --- | --- | --- | --- | --- |
| provide-evidence, send-message, make-offer, accept-claim, acknowledge-return-item, appeal, escalate | `desk` document, `filings` map, key `<disputeId>:<action>` | a claim with status `pending` or `done` already under the same key (same key for every caller, not a per-attempt id) | `claimFiling()` returns the existing row and the route answers 409 with it | `lib/desk/filing.ts` (`claimFiling`, `settleFiling`, `releaseFiling`) |
| create order, capture order (seed and demo store) | PayPal itself, via a stable `PayPal-Request-Id` (`seed-order-<invoice>`, `seed-capture-<order id>`) plus `.data/seed-state.json` | PayPal returns the first result for a repeated request id | not an error: the stored ids are reused | `scripts/seed.ts` |

The claim is released when PayPal refuses the call, so a later attempt is not blocked.
The `PayPal-Request-Id` sent with each dispute write is stored on the claim and reused if the same
filing is retried.

### Unknown outcomes

| Write | The operation you re-read with | The reference you search by | Where in the code |
| --- | --- | --- | --- |
| any dispute action | `GET /v1/customer/disputes/{id}` | the dispute id; the action counts as done when its rel is no longer in `links` or the status moved on | `lib/desk/filing.ts` (`settleUnknown`) |
| capture order | `GET /v2/checkout/orders/{id}` | order id; `status: COMPLETED` means the capture happened | `lib/paypal/sdk.ts` callers in `app/api/store` |

A request that got no response is reported as unknown, never as failed, and only after the re-read.

## Cross-operation invariants

| Invariant | Where the legal set comes from | Enforced where |
| --- | --- | --- |
| A dispute action may only be sent when its rel is in the dispute's `links` | a fresh `GET` of the dispute, read immediately before the write | `lib/desk/filing.ts` `assertAllowed()` (and the UI only renders buttons from the same list) |
| `offer_type` and `accept_claim_type` must be values PayPal offers | `allowed_response_options` on the same fresh dispute | `lib/desk/filing.ts` |
| An offer or refund may not exceed what PayPal allows | `refund_details.allowed_refund_amount`, else `dispute_amount` | `lib/rules/guards.ts` `checkOfferAmount()` |
| Evidence types sent are ones PayPal asked for | `evidences[]` entries with `source: REQUESTED_FROM_SELLER` | `lib/desk/filing.ts` `pickEvidenceType()` |
| Money decisions respect the merchant's thresholds (auto-accept ceiling, always-ask floor) | the `settings` document | `lib/rules/guards.ts` `checkThresholds()`; covered by `tests/guards.test.ts` |

All of these run before the claim is written, so a refused value never leaves a claim behind.

## Optional request fields

| Field | What requires it | Set it? |
| --- | --- | --- |
| `PayPal-Request-Id` on every POST | the duplicate-claim rows above | yes |
| `Prefer: return=representation` on create and capture | the capture id is read from the response | yes |
| `purchase_units[].invoice_id`, `custom_id` | the desk maps a dispute back to the store's records through them | yes |
| `purchase_units[].shipping` with `SET_PROVIDED_ADDRESS` | each seed order ships to its own fictional recipient | yes (seed), no (demo store, `GET_FROM_FILE`) |
| `notify_payer` on tracking | nothing | set to `false` explicitly so sandbox buyers get no mail |
| `accept_claim_reason`, `invoice_id`, `return_shipping_address` on accept-claim | nothing | left out |
| `return_shipping_address` on make-offer | only `REFUND_WITH_RETURN` offers | only then |

## When the API says no

One mapping, in `lib/api/route.ts` (`toHttp`), applied to every route:

| PayPal status | The app answers | The caller reads |
| --- | --- | --- |
| 4xx other than 401, 403, 429 | the same 4xx | PayPal's own reason (`name`, first `issue`), plus the debug id |
| 401, 403 | 502 | "PayPal refused our credentials." |
| 429 | 503 | "PayPal is rate limiting this app. Try again shortly." |
| 5xx | 502 | "PayPal had a problem. Try again." |
| no response on a write | 202 with `unknown: true`, after the re-read | what PayPal shows now |
| no response on a read | 502 | "PayPal did not answer." |

## Logging

SDK logging stays off. The app keeps its own call log (method, path, status, debug id, feature) and
never logs request bodies.

## Required reading used

`typescript-integrate-paypal` (workflow and the tables above), `typescript-getting-started` (SDK map
and file table idea, applied to the installed package's type declarations), `typescript-error-handling`
(the boundary mapping), `typescript-configuration-resilience` (retry and idempotency rules),
`typescript-testing` (assert on the request that was built, and cover no-response as well as
error-status cases).
